## Context
`RdfcDocumentCanonicalizer` hands JSON-LD to dotNetRDF, which silently drops or respells data. Whatever it drops is not signed, and a holder can change it without breaking the signature. Probes against 1.4.0 (eddsa-rdfc-2022, sign → tamper → verify) all **verified**:
- changed an undefined claim (`role: viewer → admin`) under the VCDM 2.0 context, which has no `@vocab`;
- injected a credentialSubject, refreshService, nested node or `type` entry whose IRI .NET calls malformed (`[0]`, `?filter[id]=1`, `a#b#c`);
- rewrote `issuer`/`validFrom`/`validUntil` when the issuer's own id was malformed;
- respelled an IRI (`/x/%2E%2E/users/alice`).
Controls (changing signed fields) failed as they should.

**Spec basis.**
- VC-DI 1.0 §2.4.3: implementations **MUST** throw, and **SHOULD** use `DATA_LOSS_DETECTION_ERROR`, when a JSON-LD processor drops data.
- VCDM 2.0 §5.2: a document with undefined terms **MUST** list `https://www.w3.org/ns/credentials/undefined-terms/v2` last in its `@context`.
- RDF 1.1: IRIs are compared by simple string comparison; no normalization.

**Where dotNetRDF 3.5.1 loses data** (decompiled `JsonLdParser`, `ExpandProcessor`, `NTriplesFormatter`):
1. **Expansion drops.** Undefined terms, keyword-like terms and bad language tags. Visible only through `JsonLdProcessorOptions.SafeMode` warnings.
2. **Triple-emission drops it reports:** malformed subjects (always), and types and objects (SafeMode only).
3. **Triple-emission drops it does NOT report, even in SafeMode:**
   - named graphs with a malformed name;
   - property IRIs that aren't well-formed (raw keys, or terms mapped to bad IRIs);
   - blank-node predicates;
   - `@list` members it can't convert;
   - `@direction` (ignored when `RdfDirection` is null).
   - Also not carried at all: `@index` keys.
4. **Rewriting.** `NTriplesFormatter.FormatUri` prints `Uri.ToString()`, which applies:
   - dot-segment removal;
   - unreserved and non-ASCII %-decoding (path, query, fragment);
   - scheme and host lower-casing;
   - default-port removal;
   - the `%C2%AD` trim.

**Prototype result** (scratch clone, not this repo). Every class above is rejected, each for its own reason. Well-formed input is accepted with byte-identical output: host-only URLs, non-ASCII IRIs, `%20`, `%2F`, `urn:zcap:root:` ids, DIDs, `@json`, language tags, `proof` graph containers.
- **Vectors:** zero SafeMode warnings on all 33 loadable W3C vector documents.
- **Cost:** +0.5–1 ms per canonicalization, from a second expansion.
- **Tests that break:** 146 Rdfc + 19 Legacy, all fixture issues, not regressions:
  - the issue-#33 hostile-JSON base document `{"@context":[v2],"a":1}` uses an undefined term;
  - the Legacy RDFC variant under v2 alone **drops `created`/`proofPurpose`/`verificationMethod`/`challenge`/`domain`** from the signed proof configuration (`Ed25519Signature2020` isn't a v2 term). That was a latent purpose and replay-binding bug; fail-closed now refuses it.
- **Beyond tests:** the Legacy sample and two aot-smoke steps break for the same reasons.

## Design

**`RdfcDocumentCanonicalizer.ParseJsonLd`** ([src/DataProofsDotnet.Rdfc/RdfcDocumentCanonicalizer.cs](src/DataProofsDotnet.Rdfc/RdfcDocumentCanonicalizer.cs)) runs three checks with `SafeMode = true`. Each covers what only it can see:
1. **Expansion warnings.** Read the JSON as `JsonLdParser` does (Newtonsoft, `DateParseHandling.None`), call `JsonLdProcessor.Expand(token, options, warnings)`, and treat any warning as data loss. The category comes from `JsonLdErrorCode`.
2. **Expanded-form audit.** New `Internal/JsonLdLossAudit.cs` walks the expanded `JArray` and rejects:
   - any `@id`/`@type`/property/graph-name/list-member/datatype IRI that fails dotNetRDF's own test (`Uri.TryCreate(Absolute)` plus `IsWellFormedOriginalString`);
   - blank-node predicates;
   - `@direction` and `@index` (D3).
   Language tags use `VDS.RDF.Parsing.LanguageTag.IsWellFormed`.
3. **Emission check.** Parse the **original** JSON (so the established path, and therefore canonical bytes, stay unchanged) with `parser.Warning` treated as fatal (defense in depth). Parse into a new `Internal/ExactIriStoreHandler : StoreHandler`. It overrides `HandleTripleInternal`/`HandleQuadInternal` and rejects any IRI node or literal datatype where `NQuads11Formatter.FormatUri(uri) != uri.OriginalString`. That's ground truth: it sees every quad before deduplication. `ParseNQuads` uses the same handler (D4). The handler records the fault and stops the parse; the caller throws.

**Errors (FR-23: categories only, never document content, no inner exception, since dotNetRDF's warning text quotes the content).**
- New public `JsonLdDataLossException : RdfCanonicalizationException`. This requires unsealing `RdfCanonicalizationException`, which is source-compatible.
- Fixed phrases: undefined term; not a well-formed absolute IRI; IRI would be respelled; language tag not well-formed; `@direction`/`@index`/blank-node property not carried; other ignored content.
- An N-Quads respelling throws a plain `RdfCanonicalizationException`.
- New `ProofProblemCodes.DataLossDetectionError = "DATA_LOSS_DETECTION_ERROR"` in Core.

**Suite mappings.** The pipeline already passes suite codes through.
- `RdfcCryptosuite`: create → `ProofGenerationException` with a data-loss message and the inner exception; `VerifyProof` → `DATA_LOSS_DETECTION_ERROR` (catch the subtype before the base type).
- `Bbs2023Cryptosuite`: the same for create, derive and verify. Today, verify reports any canonicalization fault as "failed unexpectedly".
- Legacy: create gets the data-loss message. Verify keeps its dual-variant codes (it fails closed either way); documented.

**Contexts (D2).** Add the two `.jsonld` files under `tests/fixtures/contexts/`, plus the `EmbeddedResource` entries in `DataProofsDotnet.Rdfc.csproj`, the `ResourceByUrl` entries, and `PROVENANCE.md` entries (each a byte-identical git pin plus a sha256).

## PR #37 review (pullrequestreview-5684898246, head 3a190a4)

The owner asked: "thoroughly address these findings if valid". Both reproduced exactly as reported, and both are now FIXED.

**P1: distinct RDF IRIs collapse in the store.**
- **Repro.** `credentialSubject: [{id: "https://e.example", name: "Alice"}]` was signed, then `{id: "https://e.example/", name: "Alice"}` appended. `VerifyProof` returned true for both suites. N-Quads `<https://e.example> <urn:p> <urn:o>` plus the `/` variant output one line.
- **Root cause.** dotNetRDF's `EqualityHelper.AreUrisEqual` compares parsed components (`PathAndQuery` is `/` for both), so `Graph.Assert` deduplicates. Each spelling passes the respelling check alone, because the formatter's trailing-slash rule preserves `OriginalString`.
  - Probed: the merge also happens for datatypes and graph names.
  - Probed, kept distinct: empty query, empty fragment and user info.
  - Literal equality goes through the same URI equality for datatypes, and through a process-wide `LiteralEqualityMode` a host could set to loose.
- **Fix.** `ExactIriStoreHandler` keeps the set of distinct statements it received, in their exact N-Quads form, before the store deduplicates. `MergedStatements` compares that count with the store's. A mismatch means data loss, with a new phrase (JSON-LD → `JsonLdDataLossException`; N-Quads → `RdfCanonicalizationException`). The check is independent of the equality rule. Exact duplicates share one form and stay harmless. Statements that merely mention both spellings keep their own spellings (verified).
- **Tests.**
  - Canonicalizer rows: subjects and datatypes.
  - N-Quads: merged input is refused; an exact duplicate is accepted; two statements keep their spellings.
  - Signature theory for both suites: the reviewer's tamper gives `DATA_LOSS_DETECTION_ERROR`; appending `/other` gives `PROOF_VERIFICATION_ERROR`; an exact duplicate verifies.

**P2: the `@base` scan rejected lossless JSON literals.**
- **Repro.** `{"@context":{"data":{"@id":"urn:data","@type":"@json"}},"@id":"urn:doc","data":{"@base":"ordinary application data"}}` was refused on 3a190a4 and accepted on 9b8f03e.
- **Fix (semantic, not syntactic).** When the input holds any non-null `@base` member, it is expanded again with every `@base` removed (contexts come from the same per-call cache). A difference outside JSON literal payloads (`@value` + `@type: @json`), or a failure of that second expansion, means a relative IRI was resolved, which is refused. So a `@base` that resolves nothing passes, and so does a `"@base"` key inside a term-coerced or explicit `@json` literal.
- **Tests.** Acceptance rows assert both literal forms verbatim. A signature theory for both suites shows the literal is signed (tampering it gives `PROOF_VERIFICATION_ERROR`). The scoped-`@base` row now resolves a relative IRI. A new row covers "@base that resolves nothing".

**Also pinned.** An NFD literal is signed as written (dotNetRDF's `NormalizeLiteralValues` defaults to false).

**Before/after.** 12 of the new or changed Issue36 cases fail on 3a190a4's source and pass now.

## PR #37 re-review (pullrequestreview-5688560817, head 1ee6c99)

Both findings reproduced here (17 new regressions fail on 1ee6c99), and both are FIXED. They had one root cause: `CollectAliases` guessed aliases from context text, comparing term values with the literal keyword and taking a scope-free union of names.

1. **P1, chained aliases bypassed the check.** With `{"s":"@set","s2":"s","i":"@index","i2":"i"}`, `s2`/`i2` were not recognized, so `{"s2":[name],"i2":"admin"}` verified with any index, and creating a proof over it succeeded. The same held for a chain on either key alone and for the `{"@id":"s"}` form.
2. **P2, an alias from a never-activated scoped context was applied globally.** It renamed a `@json`-coerced root property to `@graph`; expansion failed, and the catch reported an `@index`. Lossless documents and their unchanged `d01527a` proofs were refused.

**Redesign: the processor resolves the aliases.**
- `JsonLdLossAudit.DropsAnIndex` re-expands the input with a fresh random IRI (`urn:uuid:<guid>`, so no input can define or neutralize it) in place of every `"@index"` key outside contexts, and of every term definition (inline, scoped, or in a loaded context) whose value or `@id` is `"@index"`. This is `WithIndexAs`, served to loaded contexts through `JsonLdContextCache.Options(serve)`.
- Every alias, chains included, follows its root definition to that IRI, resolved by the processor in its own active context. A term in a scope that is never activated changes nothing.
- The probe differs from the input only at keys that expand to `@index`, and the walk already refused every `@index` that survives. So any probe failure, warning, or difference outside JSON literal payloads means one was processed and dropped: refused. In dotNetRDF a set object or value object holding a property throws (`InvalidSetOrListObject` / `InvalidValueObject`, verified in the decompiled `ExpandProcessor`), and a dropped key warns in safe mode.
- Trigger: the probe runs only when the input or a loaded context names `@index` (`NamesIndex`; no bundled context does).
- A null value's `@index` is now refused too. Expansion drops it with the value, so it was unsigned.
- Removed: `CollectAliases`, `IndexesASet`, `ReadIndexedSetsAsGraphs`, `HasIndex`, the cache's alias sets, and the `ContextView` enum.
