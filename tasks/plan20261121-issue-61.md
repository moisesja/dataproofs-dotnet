## Decisions
1. **Root cause in Core, not a rebuild per suite.** `PreviousProofReference` becomes immutable, so the options copy
   shares it. The bbs-2023 copy's `previousProof` rebuild and its "id emptied after construction" fault case go.
   The declared type is unchanged, so the public API is unchanged. A `string[]` cast now throws
   `InvalidCastException`, recorded under *Why minor* as a fix.
2. **One helper, vendored.** It goes in `JsonInputCheck`, which Rdfc and Legacy already carry verbatim, so no
   `InternalsVisibleTo` is widened and no public API is added.
3. **The pipeline copies too**, though the suites' own copies alone meet "done when". It is one line. The pipeline's
   depth and `previousProof` checks and the suite then read one object, and a third-party `ICryptosuite` is covered.
   The double clone costs little.
4. **Copy before validation**, straight after the null checks, as the issue proposed. A `ToDictionary` failure (a
   name repeated under ordinal comparison, or a null key) becomes `ProofGenerationException`, as in bbs-2023 before.
5. **Tests in a shared base** (`tests/Shared/Issue61OptionsCopyTestsBase.cs`, the Issue #33 pattern). Extension
   names are absolute IRIs so the RDFC suites can sign them (issue #36). ECDSA proofs are compared without their
   `proofValue`, because ECDSA signatures are randomized.

## Approach

### 1. Fix the root cause in Core: make `PreviousProofReference` immutable
In `src/DataProofsDotnet.Core/DataIntegrity/PreviousProofReference.cs`, `Values` will return a read-only
wrapper (`ReadOnlyCollection<string>`) built once in the constructor, not the backing array. `FromValues`
already copies its input with `ToArray()`. Equality, hashing and the JSON converter keep reading `_values`.
The property's declared type does not change, so the public API does not change. The only code that breaks
is code that casts `Values` to `string[]`: the cast now throws `InvalidCastException`.

Once the type is immutable, the options copy can share it. Nothing needs rebuilding.

### 2. One copy helper, kept identical in the three `JsonInputCheck` files
Rdfc and Legacy each carry their own copy of `JsonInputCheck` ("Keep the copies identical"), so they never
reach into Core's internals. Add the same method to all three copies:
`src/DataProofsDotnet.Core/Internal/JsonInputCheck.cs`, `src/DataProofsDotnet.Rdfc/Internal/JsonInputCheck.cs`
and `src/DataProofsDotnet.Legacy/Internal/JsonInputCheck.cs`.

```csharp
// A copy of the proof options that shares nothing with the caller's object (issue #61) …
public static DataIntegrityProof OwnedCopy(DataIntegrityProof options)
    => options with
    {
        Context = options.Context is { } c ? Own(c) : null,
        AdditionalProperties = options.AdditionalProperties?.ToDictionary(m => m.Key, m => Own(m.Value), StringComparer.Ordinal),
    };   // the ArgumentException for a repeated name becomes a ProofGenerationException, as in bbs-2023 today
// Own: Clone(), except an Undefined element is kept as it is, so the later check reports it.
```

This is `Bbs2023Cryptosuite.CopyOptions` (`Bbs2023Cryptosuite.cs:374`) without the `previousProof`
rebuild, which step 1 makes unnecessary. `Type` and the other scalar members are copied by the record
`with`.

### 3. Copy at every create entry point, before anything reads the options
Each entry point below gets `proofOptions = JsonInputCheck.OwnedCopy(proofOptions);` straight after its
`ArgumentNullException` checks:
- `JcsCryptosuite.CreateProofAsync`, which covers eddsa-jcs-2022 and ecdsa-jcs-2019;
- `RdfcCryptosuite.CreateProofAsync`, which covers eddsa-rdfc-2022 and ecdsa-rdfc-2019;
- `LegacyCryptosuiteBase.CreateProofAsync`, which covers both legacy suites in both variants;
- `DataIntegrityProofPipeline.AddProofAsync`. This is one line. It gives the pipeline's own checks (the
  depth budget, the `previousProof` lookup) and the suite the same object, and it protects a third-party
  `ICryptosuite` registered with the pipeline. The suite copies again, which costs little.
- `Bbs2023Cryptosuite.ValidateBaseProofRequest`: its private `CopyOptions` is deleted and the call
  switches to the shared helper.

The emitted bytes do not change. The one observable change is that the returned proof no longer shares
the caller's dictionary or `JsonElement`s.

### 4. Tests
- **Shared base**: new `tests/Shared/Issue61OptionsCopyTestsBase.cs`, linked into the Core, Rdfc and Legacy
  test projects the way `Issue33SuiteCreateTestsBase.cs` is. Each subclass supplies the suite, a signer, the
  public key, valid options, a document, and a document without `@context`. The base reuses the issue's
  `MutatingSigner`. Extension names are absolute IRIs (`https://example.org/vocab#note`), because RDFC
  refuses terms it would drop (issue #36). It runs these cases, directly and through the pipeline:
  1. A signer that, during `SignAsync`, sets `Type`, changes the note and adds a `proofValue` extension:
     the proof has the type and note that were asked for and no extension `proofValue`. Its members other
     than `proofValue` equal those of a proof made from untouched options (ECDSA signatures are
     randomized), and it verifies.
  2. Changing the options after the call leaves the proof unchanged. This case runs directly only, because
     the pipeline returns JSON.
  3. Extension values and the fallback `@context` are taken from `JsonDocument`s that are disposed after
     the call. The proof still serializes, to the expected JSON.
- **Subclasses**: in Core.Tests, eddsa-jcs-2022 and ecdsa-jcs-2019. In Rdfc.Tests, eddsa-rdfc-2022 and
  ecdsa-rdfc-2019. In Legacy.Tests, both suites in both variants. bbs-2023 keeps its existing tests in
  `Bbs2023KeyStoreTests.cs`.
- **`PreviousProofReferenceTests`** (Core): `Values` is not a `string[]`. Writing through `IList<string>`

- **`Bbs2023KeyStoreTests.cs`**: three places cast `Values` to `string[]` (lines 520, 619 and 648), which

### PR #62 review, round 1 (review 6006778877 on 2bef74d, 2026-11-21 17:01Z)
- **[P2] `PreviousProofReference` was still mutable. Fixed.** `ReadOnlyCollection<T>`'s non-generic
  `ICollection.SyncRoot` returns the array it wraps, so `(string[])((ICollection)r.Values).SyncRoot` rewrote the ids
  without reflection. Removing bbs-2023's rebuild had therefore regressed it: a caller's change rewrote an issued base
  proof, and the next derivation failed. This was my mistake. I assumed `ReadOnlyCollection` hides its list, and
  tested only the routes I had thought of.
  - **The fix.** `Values` returns a private `ReadOnlyIds` that implements only `IReadOnlyList<string>`. Its iterator
    enumerator does not expose the array.
  - **Mutation coverage restored.** `Issue61OptionsCopyTestsBase.TryToRewrite` tries every public write route
    (`string[]`, `IList<string>`, `ICollection<string>`, `IList`, `SyncRoot` as `string[]` and as `IList`) and
    asserts that each is refused. It runs while the signer or store runs and again after the call:
    - on every suite in the shared base (single and array form);
    - in bbs-2023 for both overloads, where it also asserts that the serialized proofs are unchanged and that both
      still derive.
  - **The interface set is pinned.** A Core test fixes the exact interfaces that `Values` implements, for every way
    a reference is made (`FromSingle`, `FromValues`, implicit, JSON string, JSON array).
  - **Checked against the old code.** All 28 new or rewritten runs failed on 2bef74d's `PreviousProofReference.cs`,
    and they pass now. 4,243 tests, 0 failed, 0 skipped.


### PR #62 review, round 2 (review 6007474359 on 0da55a9, 2026-11-21 18:59Z)
- **[P2] `FromValues` kept an array the caller's code had been handed. Fixed.** `Enumerable.ToArray` passes the
  array it returns to the `CopyTo` of a source that implements `ICollection<T>`, and `FromValues` stored that array.
  A collection that kept it could rewrite the reference with no cast at all. The bbs-2023 regression from round 1
  therefore still reproduced, and so did both outcomes issue #61 was opened for, on every suite and the pipeline.
  This was my mistake a second time: I checked "immutable" from the reading side only.
  - **The fix.** `FromValues` clones the array `ToArray` returns and checks the clone, so no caller code ever holds
    the array the reference keeps.
  - **Tests.** A `CapturingIds` collection in the shared file keeps the array its `CopyTo` is handed.
    `CallersPreviousProof(form)` builds a reference in one of three ways (string, array, array from the caller's
    collection) and returns an action that makes every write its caller can try. It is used in the shared
    direct-suite theory, in a new pipeline theory (a chain of two proofs plus a third that names them), in the
    bbs-2023 theory for both overloads, and in a Core unit test. The legacy JCS variant has no proof chain, so its
    pipeline rows assert the documented refusal.
- **[P3, predates the PR] bbs-2023 mandatory pointers: the same route. Fixed here.** `mandatoryPointers.ToArray()`
  had the same flaw, and the store or a canonicalizer of the caller's runs between grouping and packing. Folded in,
  as the reviewer recommended, because it is the same defect and the same one-line fix, and because this PR's
  CHANGELOG bullet ("Copies at entry") claims it. A new theory covers both overloads: the key store, and a
  caller's `IRdfCanonicalizer` for the raw-key overload.
- **Checked against the old code.** With 0da55a9's `PreviousProofReference.cs` and `Bbs2023Cryptosuite.cs` restored,
  18 runs fail: every "array from the caller's collection" row (direct and pipeline, on every suite; bbs-2023), the
  Core fact, and both mandatory-pointer rows. All pass with the fix.
- **Smaller points.** `TheProof_OutlivesTheCallersJsonDocuments` now says why it compares bytes and does not verify:
  its input has the follow-up (b) shape. New commit subjects stay under 72 characters. The five pushed subjects are
  left as they are, because rewriting pushed history is the owner's call.
- **Not folded in (owner's call).** Follow-up (a), the pipeline reading the caller's document after the await: the
  reviewer recommends folding it in. It concerns the document, not the options this issue is about, so it stays a
  follow-up under the PR-scope rule. Follow-up (b) gets its own issue. A third one surfaced in the sweep, (c):
  `DeriveProof` uses the caller's `selectivePointers` several times without copying them, and its combined pointer
  list (`Concat(...).ToList()`, which uses `List.AddRange`) hands its internal array to the caller's `CopyTo`. A
  custom canonicalizer runs in between, so the holder can get a derived proof that does not verify. This is
  holder-side, predates the PR, and is outside the options copy.
- **Lesson.** Before claiming that an object shares nothing with its caller, list every piece of the caller's code
  that runs while the object is built, not only what it exposes afterwards. In .NET, that includes the `CopyTo` and
  enumerator of any collection passed in. `tasks/lessons.md` is unchanged on purpose: the owner's checkout has
  uncommitted edits to it.
- **Adversarial pass on 24f8268.** A sub-agent got the diff and the guarantee, not my conclusions. It found no route
  around the options copy. These held under probes:
  - an extension enumerator that rewrites the bytes behind a value it has yielded (this fails on e4e3026);
  - a pipeline suite that rewrites the pipeline's copy;
  - a key store that clears everything it was handed;
  - a `MemoryManager` HMAC key, which is read once;
  - the interface set of `Values`;
  - legacy RDFC against a `KeyType` getter.

  `OwnedCopy` is textually identical in all three copies. It found three older routes of another class: caller code
  runs between two reads of a value the caller controls. All three reproduce on e4e3026, and all fail closed (the
  proof does not verify or derive). Not folded in; reported as follow-up (d):
  - **d1, bbs-2023 raw-key overload.** It reads the private key twice: `PublicKeyOf` before the caller's canonicalizer
    runs, `Sign` after it. A canonicalizer that rewrites the caller's key array, or a `MemoryManager` key, packs one
    key's public key with another key's signature. Fix: read the key once, after the last caller code, or check the
    signature as the key-store overload does.
  - **d2, `DeriveProof`.** It reads `presentationHeader` twice, across the canonicalizer. Fix: copy it at entry.

  Informational: `JsonElement.Clone()` returns the element itself when its document is not disposable. Those bytes
  are immutable in safe code.
