## Context
Issue #33 is **valid**. Every row reproduces at `cd04a76` through both `eddsa-jcs-2022` and
`eddsa-rdfc-2022`. I checked it with scratch harnesses wired to the real Core, Rdfc and Legacy projects
(in the session scratchpad: spike33, spike33b, spike33c).

**Reproduced as reported.**
- **`Verify` and `VerifyAsync`:** a top-level `\uD800` member name throws `InvalidOperationException`.
  The throw comes from line 260 (`TryGetProperty("proof")`) or line 435, depending on member order.
  The resolver is never called.
- **Chain lookup:** a chain whose referenced proof has `id: "\uD800"` throws `InvalidOperationException`
  from `GetProofId` (line 474).
- **`AddProofAsync`:** throws a raw exception for each listed row. A member name throws
  `InvalidOperationException` (line 459). A duplicate throws `ArgumentException` (line 97). A string value
  or depth over 64 throws `JsonException` (line 116). `previousProof` over a `\uD800` id throws
  `InvalidOperationException` (line 104).

**Found beyond the report. Same class, all pre-existing.**
1. **Pipeline, verify:**
   - A member name in a non-UTF-8 document (`JsonDocument.Parse(bytes)` accepts 0xFF) throws
     `InvalidOperationException`. This is the #28 class.
   - A `\uD800` member name in a *different* proof of a chain throws, from `TryGetProperty("id")`.
2. **Pipeline, add:**
   - A non-UTF-8 member name throws `InvalidOperationException`.
   - A `\uD800` name or value inside an existing proof throws `JsonException`.
   - An object-form existing proof at depth 64 throws `JsonException`, because the chain re-embeds it
     one level deeper.
   - **Proof options:** a `\uD800` in `AdditionalProperties` or `Context` throws `JsonException`.
   - **Proof options:** an extension key that collides with a modelled member serializes as a
     *duplicate* `proofPurpose`.
3. **Pipeline, inconsistent outcomes** for the same class: per-proof `PROOF_TRANSFORMATION_ERROR`,
   "could not be parsed", or "Verification failed unexpectedly". RDFC also **signs and verifies**
   documents with nested duplicates or non-UTF-8 string values. dotNetRDF silently picks a value, which
   makes it a parser differential.
4. **Direct suite entry points** (public, documented to throw `ProofGenerationException`):
   - Every suite's `CreateProofAsync` throws `JsonException` on untranscodable proof options.
   - The Legacy suites' `CreateProofAsync` (JCS variant) throws `InvalidOperationException`,
     `JsonException` or `ArgumentException` on a hostile document.
   - **bbs-2023 `CreateBaseProofAsync` and `DeriveProof`** throw a raw exception for every class:
     `InvalidOperationException`, `JsonException`, `ArgumentException` or `JsonReaderException`.
     `DeriveProof` runs on a holder's wallet over a document an issuer sent.

**Spike facts the design rests on.**
- `JsonMarshal.GetRawUtf8Value(element)` gives the element's UTF-8 bytes without a copy.
- `Utf8JsonReader` (MaxDepth 64), `JsonDocument` and the serializer all accept depth 64 and reject 65.
- **Comments and trailing commas** survive in a lenient-parsed element's raw text, and such documents
  **verify today**. The guard must skip them, not reject them.
- The prototype guard rejects all four lone-surrogate escapes, an escaped duplicate (`a` and its `\u0061` escape),
  a nested duplicate, non-UTF-8 bytes and depth 65. It passes a surrogate pair, a BMP escape, `\/`, raw
  non-BMP text, the same name in sibling objects, comments and trailing commas.
- Cost: 4.7 µs on the 912-byte W3C `windDoc` and 3 ms per MB. That is about the same as the
  `JsonObject` round trip the pipeline already does per proof.

**Normative basis for rejection.**
- RFC 8785 §3.1: "JSON objects MUST NOT exhibit duplicate property names" and "JSON string data MUST be
  expressible as Unicode".
- RFC 8785 §3.2.2.2: lone surrogates "MUST cause a compliant JCS implementation to terminate with an
  appropriate error".
- RFC 8259: §4 says names "SHOULD be unique" and receiver behaviour is otherwise "unpredictable";
  §8.1 requires UTF-8; §8.2 calls unpaired surrogates "unpredictable".
- RFC 7493 (I-JSON): §2.1 and §2.3 forbid both.

## Decisions (strike any you disagree with)
1. **Scope: the pipeline (the issue) plus the sibling create-side entry points.** That covers the
   `CreateProofAsync` of the JCS, RDFC and Legacy suites, and bbs-2023's `CreateBaseProofAsync` and
   `DeriveProof`. It is the same input class on the same documented contract. The lessons apply:
   "grep the sibling decoders; four had it", and same-class findings are in scope. The sibling work goes
   in its **own commit** so it can be dropped independently. *If struck:* pipeline only, and I file a
   follow-up issue for the rest.
2. **One guard, run before anything touches the JSON.** Each public entry checks its JSON inputs (the
   document, and the serialized proof options or configuration) once, up front. The checks are:
   - the text is valid UTF-8;
   - every escaped string and member name transcodes;
   - no object has a duplicate member name at any depth, compared after unescaping;
   - depth is at most 64.

   Comments and trailing commas are skipped. The issue's step 1 is this design.
3. **Verify-side result shape:** a hostile document returns a **document-level**
   `PROOF_TRANSFORMATION_ERROR`, before any proof is parsed or any resolver is called. The code stays
   the same; what changes is that the problem moves from per-proof to document-level. Three existing
   tests change deliberately:
   - `Verify_DuplicateTopLevelMember_…`
   - `Verify_OversizedHostileDocument_…`
   - `Verify_UntranscodableProofExtension_ThroughThePipeline_…`

   The last one is the PR #32 re-review pin that asked for broadening to be "a visible decision". This
   is that decision. The suite-level pins in `JcsTransformationFailureTests` are untouched.
4. **Accept-set narrowing, as minor material inside the already-minor 1.4.0.**
   - JCS already rejected these inputs through NetCid, except non-UTF-8 string values, which it signed.
   - RDFC and the Legacy RDFC variant accepted nested duplicates and non-UTF-8 values. Rejecting them
     is a spec-valid narrowing under RELEASING.md, because RFC 8259 only says SHOULD.
   - **Own earlier output now rejected:** documents this library secured from caller input that held a
     nested duplicate (RDFC) or a non-UTF-8 string (any suite). The CHANGELOG will name this.
5. **Sharing without widening internals.** The guard is a Core `internal` class. It is vendored
   verbatim into `Rdfc/Internal` and `Legacy/Internal`, following the `EcdsaSignatureEncoding`
   precedent and PRD §2 ("No package reaches into another's internals").
   - It adds no public API.
   - Jose's `JoseJson.RequireTranscodableJson` stays separate. It throws a different exception type,
     and Jose checks duplicates through its parse options.
6. **Defence in depth (issue step 2), with one deviation.**
   - Widen the line-444 filter to include `InvalidOperationException`.
   - Wrap the chain lookup in the same mapping, keeping it ahead of key resolution so a dangling
     reference still calls no resolver.
   - On the add side, wrap the pipeline's own transformation and output assembly. A cause is attached.
   - **Deviation:** the `suite.CreateProofAsync` call is *not* wrapped. Otherwise a signer's
     `InvalidOperationException` or `ArgumentException` would be relabelled as a document fault.

## Implementation
1. **`src/DataProofsDotnet.Core/Internal/JsonInputCheck.cs`**
   - `string? FindProblem(JsonElement)` returns a fixed phrase that never contains document content
     (FR-23): "is not valid UTF-8", "contains a JSON escape for an unpaired UTF-16 surrogate", "has a
     duplicate member name", or "nests deeper than 64 levels".
   - `RequireValid(JsonElement, string what)` throws `ProofGenerationException($"{what} {problem}.")`.
   - `SerializeChecked(DataIntegrityProof, JsonTypeInfo<…>, string what)` maps a `JsonException` to a
     `ProofGenerationException`, then runs the check.
2. **`DataIntegrityProofPipeline`**
   - In `AddProofAsync`, guard the document and the options after the existing argument checks. Then
     wrap the pipeline-owned steps: lines 92–116 and lines 118–137.
   - In `VerifyCoreAsync`, guard after the object check and return `DocumentFailure(ProofTransformationError, …)`.
   - Widen the line-444 filter and wrap the chain lookup.
   - Update the type remarks.
3. **`JcsCryptosuite.CreateProofAsync`:** guard the document. Serialize the proof configuration
   through `SerializeChecked`, which also covers an extension key colliding with a modelled member.
4. **Rdfc**
   - Vendor the guard into `Internal/JsonInputCheck.cs`.
   - Apply it in `RdfcCryptosuite.CreateProofAsync` to the document and the configuration.
   - Apply it in `Bbs2023Cryptosuite`: `CreateBaseProofAsync` gets the document and configuration;
     `DeriveProof` gets the document before `SplitProof`.
5. **Legacy:** vendor the guard, and apply it in `LegacyCryptosuiteBase.CreateProofAsync` to the
   document and the configuration, for both variants.
6. The suites' `VerifyProof` methods are unchanged. They already fail closed through their catch-alls.

## Decisions during implementation

- **Proof options are checked raw, then serialized (refines Implementation step 1).** The first run
  showed an options extension holding non-UTF-8 bytes being *signed*: System.Text.Json's writer rewrites
  invalid UTF-8 in a `JsonElement` as `\uFFFD` (spike33d), so a check over the serialized form alone
  never sees it. A `default(JsonElement)` in the options makes serialization throw a raw
  `InvalidOperationException` on every create path (pre-existing). `SerializeChecked` now checks each raw
  `@context`/extension element first (rejecting `Undefined` as "has a member with no JSON value"), then
  serializes (a `JsonException` → "could not be serialized as JSON"), then checks the serialized form
  (catches an extension member that repeats a modelled name, which the serializer writes twice).
- **Option messages use "The proof options object …"** so the singular predicate phrases read correctly.
- **Shared test matrices instead of three copies.** `tests/Shared/HostileJson.cs` (builders; every escape
  built at run time; every splice asserts it changed the text), `Issue33PipelineTestsBase` (verify/add
  matrix; derived per suite in Core.Tests and Rdfc.Tests) and `Issue33SuiteCreateTestsBase` (direct
  `CreateProofAsync`; derived for all eight create paths), linked as `<Compile Link>` items. A test-only
  pattern; no `src/` file is shared.
- **Corrected claim — earlier non-UTF-8 output still verifies.** The plan's Decision 4 said documents
  secured from non-UTF-8 input would now be rejected. Observed against `cd04a76` (spike33e/f): the
  pre-fix `AddProofAsync` output carries `\uFFFD` and verifies under the fix. What *is* rejected:
  nested-duplicate documents from `eddsa-rdfc-2022` and the legacy JCS suite (also checked), and — found
  by a pre-fix probe (spike33g) — proofs from RDFC/legacy suites given options whose extension member
  repeats a modelled name (emitted with two `proofPurpose` members).
- **CHANGELOG table rows were each observed on the pre-fix code** (spike33g), which corrected three
  draft claims: the JCS suites refused (not signed) the colliding extension; the RDFC suites and the
  legacy RDFC variant *threw* on a non-UTF-8 document value while the legacy JCS variant signed it as
  U+FFFD; and bbs-2023 `DeriveProof` *accepted* a non-UTF-8 string value (every other bbs case threw).
- **PRD:** FR-2's new paragraph names every create entry point that runs the check, so FR-4 and FR-11
  got no separate sentence (the plan listed them); FR-3 and FR-12 did.
- The VS Code Git integration published the branch at its base (`1bb35ac`) on creation; none of this
  work was pushed by it.
