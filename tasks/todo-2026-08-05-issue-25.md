# Issue #25 — JWS `kid` in the unprotected per-signature header (v1.3.0)

Branch: `fix/issue-25-jws-kid-unprotected`
Issue: <https://github.com/moisesja/dataproofs-dotnet/issues/25> (milestone 1.3.0)
Plan approved: 2026-08-05.

## Problem

1.2.0 (issue #17) removed the RFC 7515 §7.2.1 duplication by making `kid` **protected-only**.
DIDComm v2.1 signed envelopes carry it in the **unprotected per-signature** header, so
didcomm-dotnet's outbound signed interop went from 1-of-2 reference implementations to 0-of-2:

- didcomm-jvm 0.3.2 — `MalformedMessageException: JWS Unprotected Per-Signature header must be present`.
- didcomm-python 0.3.2 — `core/validation.py` requires `signatures[0].header.kid`.

## What the specs say (researched before deciding)

- **RFC 7515 §4.1.4** — `kid` is a *hint*; use is OPTIONAL; no placement rule.
- **RFC 7515 §6** — "if the only information used in the trust decision is a key, these parameters
  need not be integrity protected, since changing them in a way that causes a different key to be
  used will cause the validation to fail." → an unprotected `kid` is explicitly conformant.
- **RFC 7515 §7.1** — compact serialization has no unprotected header; `kid` can only be protected.
- **RFC 7515 §7.2.1** — the two parameter-name sets MUST be disjoint (already enforced: emit #17,
  accept #19).
- **DIDComm v2.1** — normative MUSTs cover the media type and that `kid` be a DID URL, *not*
  placement; but Appendix C.2's examples are uniformly `protected:{typ,alg}` + `header:{kid}`, and
  both reference implementations require that shape.
- **W3C VC-JOSE-COSE** — no placement rule; examples use a protected `kid`, over compact JWS.

Conclusion: no spec mandates a global move. Make placement selectable, default it from the
declared media type.

## Scope addition, approved mid-implementation

Verifying the kid fix against didcomm-python's actual source turned up a **second** blocker that
issue #25 does not mention. `unpack_sign` (`didcomm/core/sign.py`, v0.3.2) calls `validate_jws` on
the **raw** envelope dict, and `didcomm/core/validation.py` rejects anything without a
`signatures` array — before authlib normalizes the serialization. `JwsBuilder` flattens a
single-signer JSON JWS, so didcomm-python would still have rejected our envelopes with
`MalformedMessageError` even with the kid in the right place; the kid fix alone would have left
interop at 1-of-2, not 2-of-2. didcomm-jvm is unaffected (nimbus normalizes both forms).

Approved 2026-08-05: also emit the **General** form for a single signer when `typ` is the DIDComm
signed media type, scoped to that media type so nothing else changes.

## Review

### What shipped

`JwsKidPlacement { Auto, Protected, Unprotected }` on `JwsSigner`. `Auto` — the default — resolves
to the unprotected per-signature `header` when a JSON serialization is used *and* `typ` is
`application/didcomm-signed+json` (or the bare `didcomm-signed+json`); to the protected header
otherwise; and always to the protected header in compact serialization, which has none.
`Protected`/`Unprotected` force the choice; `Unprotected` + `BuildCompactAsync` throws when the
signer carries a kid, rather than silently signing a kid the caller asked to leave unsigned.
The DIDComm media type additionally selects the General serialization for a single signer.

`JwsParser` needed no change for the placement itself — it has read the unprotected kid first with
a protected fallback since #10, and enforced §5.2-step-4 disjointness since #19 — but gained
`JwsParseResult.SignerKidIsProtected` in response to the adversarial review (below).

### Adversarial review — two passes, six defects, all fixed

**Pass 1** found four, all reproduced independently before acting:

1. **Signer-identity substitution [MEDIUM].** The safety argument for an unprotected kid holds only
   while the caller's resolver is injective. When one DID document lists the same key under two
   verification-method ids — ordinary — an intermediary can relabel the kid between them, the
   signature still verifies, and `SignerKid` reports the attacker's choice. It disproved the
   CHANGELOG's "denial of service, not forgery" claim, which I had written. **Not** fixed by
   reverting the DIDComm shape (that re-breaks interop); fixed by adding
   `JwsParseResult.SignerKidIsProtected` so a verifier can require a signed kid and fail closed,
   plus rewriting the security note to state §6's *precondition* rather than only its exemption.
2. **`{"alg":"EdDSA","kid":null}` crashed the parser [MEDIUM].** The kid reaches the caller's
   resolver *outside* `JwsParser`'s try block, so a resolver dereferencing it threw
   `NullReferenceException` straight through the documented contract. Pre-existing, same class as
   #15, remote and unauthenticated. Fixed in `JwsProtectedHeader`.
3. **XML docs contradicted the compact + `Unprotected` behavior [LOW].** Docs corrected.
4. **Two different JSON encoders rendered the two headers [INFORMATIONAL].** Fixed by passing
   `JoseJson.Default` to `ToJsonString()`.

**Pass 2**, reviewing those fixes, found that **fix 2 had introduced a regression of the same class
it closed**: `TryGetProperty` throws `InvalidOperationException` on a non-object root, and placing
it before deserialization meant a protected header of `[1,2]`, `"x"`, `123`, `true`, or `null`
escaped as `InvalidOperationException` on `JwsParser.Parse`, `ParseCompact`, *and*
`VcJose.VerifyCredential`. Strictly easier to reach than the bug it replaced — no resolver
behavior needed. The 413-test suite was green throughout, because nothing covered a non-object
root. Fixed with an explicit root-kind guard plus an `InvalidOperationException` catch, which also
closes a pre-existing invalid-UTF-8-property-name escape on the JSON path.

Pass 2 also confirmed `SignerKidIsProtected` is correct across 16 paths and could not construct the
dangerous inversion (unprotected-sourced kid reported as protected), and flagged one accepted
residual: the flag describes the first *verifying* signature, so reordering a mixed-placement
`signatures[]` can flip it. That only ever rejects, never over-trusts; documented on the member.

### Residual, accepted and documented

With `Unprotected`, the kid is not covered by the signature, so an intermediary can strip it
(envelope fails to verify) or relabel it to another identifier resolving to the same key
(verification succeeds, reported identity changes). This is inherent to DIDComm v2.1 — every
conformant implementation carries it — and `SignerKidIsProtected` is the control. `Protected`
remains the default for every non-DIDComm media type.
