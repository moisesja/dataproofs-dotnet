## Owner's intent

Evaluate the issue and, if valid, address it thoroughly. Ship as 1.4.0; do not tag or publish.

## Verdict: valid, and broader than reported

Reproduced in a scratchpad console project against `main` with a genuinely signed Ed25519 header:

| Protected-header input | `JwsParser.Parse` (Flattened + General) | `ParseCompact` | `VcJose.VerifyCredential` |
| --- | --- | --- | --- |
| valid member name (control) | verified | verified | verified |
| invalid-UTF-8 **member name** (`FF FE`) | `MalformedJoseException` | **verified** | **verified** |
| invalid-UTF-8 **string value in an extension member** | **verified** | **verified** | **verified** |
| invalid-UTF-8 in the `kid` value | rejected | rejected | rejected |

Row 2 is the issue. Row 3 is new: the JSON path's rejection was never a UTF-8 check, only a side
effect of `EnumerateObject()` transcoding member *names* for the #19 disjointness check — which
the compact path skips on purpose. Extension *values* are cloned as `JsonElement` and never
transcoded. Root cause: nothing validated the decoded octets as UTF-8 (RFC 7515 §5.2 step 3).

Same omission in every other decode→parse site in the package:

| Decoder | Before | Pre-signature? |
| --- | --- | --- |
| `SdJwt/CompactJwt.DecodeJsonObject` | raw `InvalidOperationException` out of `SdJwtVerifier.Verify` / KB check | **yes** |
| `SdJwt/Disclosure.Parse` | raw `InvalidOperationException` out of `SdJwtVerifier.Verify`; array-element value accepted | **yes** |
| `Jwt/JwtClaims.Parse` | raw `InvalidOperationException`, through `JwtHandler.Verify`; unregistered value accepted | post-signature (direct `Parse` is public) |
| `Encryption/JweProtectedHeader.Decode` | name accepted as U+FFFD; extension value accepted | pre-decrypt, AAD-bound → sender only |
| `JwsParser.Parse(string)` / `JweParser.Parse(string)` with a lone surrogate | raw `ArgumentException` | caller's own text only |

## Decisions

1. Fix (the issue offered "fix or correct the CHANGELOG"): the RFC requires the check; one line
   per decoder.
2. One shared helper, `JoseJson.RequireUtf8`, applied at every decode→parse site. Keeps the compact
   path's no-enumeration performance choice (`Utf8.IsValid` is a vectorised scan).
3. Issue fix and same-class sweep in separate commits, each with its own rollback decision.
4. **Version 1.4.0 — owner's decision.** RELEASING.md's accept-set rule would say patch; the owner
   elected minor because the narrowing spans four decoders and changes the exception contract on
   two pre-auth paths. Recorded as a worked example in RELEASING.md and a "why minor" paragraph in
   the CHANGELOG. No tag, no publish.
5. Dated in-place correction of the 1.3.0 CHANGELOG claim, not a silent rewrite.
6. Lessons entry: a claim naming N entry points is N claims, each needing a test.

## Appendix — drafted follow-up issues (not filed)

### Exception-contract escapes not covered by #28: lone-surrogate JSON escapes, non-object JWT claims root, empty JWE protected header

Label: `bug`

#### Summary

`SdJwtVerifier.Verify`, `SdJwtVcVerifier.VerifyAsync` and `JwtHandler.Verify` are documented as never throwing for an invalid token. `JwsParser`, `JweParser`, `VcJose.VerifyCredential`, `JwtClaims.Parse`, `Disclosure.Parse` and `SdJwtComponents.Parse` are documented to fail only as `MalformedJoseException` or `JoseCryptoException`. Three input classes still break those contracts, most of them before any signature check. They were found by the adversarial review of #29 (issue #28), and all three predate it. #29 deliberately closes only the invalid-decoded-octet class, so these are tracked here.

#### 1. Lone-surrogate JSON escapes (`\uD800`, `\uDC00`, `\uD800A`)

The six ASCII bytes `\uD800` are valid UTF-8, so the #28 check passes them. RFC 8259 §8.2 permits an unpaired surrogate escape in the grammar, and `Utf8JsonReader` / `JsonDocument.Parse` accept it. System.Text.Json defers the UTF-16 check to the transcode, which then throws `InvalidOperationException` ("Cannot read incomplete UTF-16 JSON text as string with missing low surrogate"). That transcode happens in `JsonElement.GetString()`, in `TryGetProperty` and `EnumerateObject()` (both compare member names), in `JsonNode` key enumeration, in `JsonValue.GetValue<string>()` and in `ToJsonString()`. Only decoders that go through `JsonSerializer` are safe, because it rethrows the fault as `JsonException`. That covers `JwsProtectedHeader`, `JweProtectedHeader` and `Jwk`.

**Reachable without a signature** (reproduced on the #29 head):

```csharp
static string B(string s) => Base64Url.Encode(Encoding.UTF8.GetBytes(s));
SdJwtVerifier.Verify(B("""{"alg":"EdDSA","\ud800":1}""") + "." + B("{}") + ".AA~", _ => null);
// InvalidOperationException: Cannot read incomplete UTF-16 JSON text as string with missing low surrogate.
```

- `SdJwtVerifier.Verify`: the issuer header's `alg`, `kid` or a member name (`SdJwt/CompactJwt.cs` around `alg`/`KeyId`; `KeyId` is read in `SdJwtVerifier.Verify` outside any `try`). It also fires on the payload's `_sd_alg` or a member name (`SdJwt/SdJwtClaims.cs`), and on an appended Disclosure claim name over a valid issuance (`SdJwt/Disclosure.cs`, `ParseObjectProperty`).
- `SdJwtVcVerifier.VerifyAsync`: `issuerJwt.Type` is read outside the `try`.
- `JwsParser.Parse`, Flattened, General and detached: the `payload`, `protected` and `signature` strings, the unprotected `header.kid`, an unprotected member name, or even an extra top-level member name.
- `JweParser.Parse` / `PeekRecipients` / `ParseAsync`: `RequireString` calls `GetString()` on `protected`, `iv`, `encrypted_key` and `recipients[].header.kid`.
- `VcJose.VerifyCredential`: the `cty` extension value (`ctyEl.GetString()`, outside any `try`).

**After a valid signature** (a malicious issuer or holder):

- The Key Binding JWT's `typ`, `aud`, `sd_hash` and `nonce`.
- The issuer-signed `_sd` digests and the `"..."` placeholders.
- `cnf.jwk` (via `ToJsonString()`).
- `JwtHandler.Verify` with `\uD800` in `iss`, `sub`, `jti`, `aud`, any claim name or a nested key.

**Model poisoning:** a signed JWT with payload `{"iss":"i","x":"\uD800"}` gets `JwtHandler.Verify` → `IsValid == true`. Then `result.Claims.AdditionalClaims["x"].GetValue<string>()`, `ToJsonString()` or `ToJsonBytes()` throws `InvalidOperationException` in the consumer's code.

**Not affected:** a JWS protected-header member name lands in the `catch (InvalidOperationException)` in `JwsProtectedHeader.DecodeCore`, which is therefore load-bearing. JWE header modelled fields fail as "not valid JSON" through the serializer.

**Suggested fix.** After the existing `JoseJson.RequireUtf8` call, run one eager pass with `Utf8JsonReader` that calls `GetString()` on every `PropertyName` and `String` token. Map an `InvalidOperationException` there to `MalformedJoseException("… contains an invalid UTF-16 escape sequence.")`. That pass is O(n), and the reader also validates structure. Apply it at every base64url-decoded JSON site and to the outer JSON text in `JwsParser.ParseJsonCore` / `JweParser.ParseStructure`. Then add defence-in-depth catches, or move reads inside the existing `try`, at the sites listed above.

#### 2. `JwtClaims.Parse` with a non-object JSON root

`JsonObject.Create(doc.RootElement.Clone())` throws `InvalidOperationException("The element must be of type 'Object'")` for `[]`, `42`, `"x"` and `true`. The `node is not JsonObject` guard after it only ever sees the `null` literal. Through `JwtHandler.Verify` this needs a validly signed token, but `JwtClaims.Parse` is public, with a documented `MalformedJoseException` contract.

```
JwtClaims.Parse([])                      InvalidOperationException: The element must be of type 'Object'
JwtClaims.Parse(null)                    MalformedJoseException: JWT claims set is not a JSON object.
JwtHandler.Verify(signed, payload = [])  InvalidOperationException: The element must be of type 'Object'
```

Fix: check `doc.RootElement.ValueKind != JsonValueKind.Object` before `JsonObject.Create`.

#### 3. `JweParser` with `"protected": ""`

`RequireString(root, "protected")` accepts the empty string, and `JweProtectedHeader.Decode` then calls `ArgumentException.ThrowIfNullOrEmpty(encoded)`. That throws `ArgumentException` through `Parse`, `PeekRecipients` and `ParseAsync`, before any key work. The JWS counterpart already returns `MalformedJoseException("JWS protected header is empty.")`.

```
JweParser.Parse(protected="")      ArgumentException: The value cannot be an empty string. (Parameter 'encoded')
JwsParser.Parse(protected="")      MalformedJoseException: JWS protected header is empty.
```

Fix: make the empty check in `JweProtectedHeader.Decode` throw `MalformedJoseException`, mirroring `JwsProtectedHeader.DecodeBytes`.

#### Acceptance

- Regression tests for `\uD800`, `\uDC00` and `\uD800A` at member-name, modelled-string, extension-value and outer-JSON-member placements, on every entry point listed above, including the Key Binding JWT path end to end.
- Tests for each non-object root through `JwtClaims.Parse` and `JwtHandler.Verify`, and for an empty JWE `protected` through all three `JweParser` entry points.
- Each test shown to fail with the fix reverted.

### Cose: CBOR text strings that are not valid UTF-8 are decoded lossily (Lax conformance) instead of rejected

Label: `bug`

#### Summary

The COSE decoders read with `CborConformanceMode.Lax` (`src/DataProofsDotnet.Cose/Internal/CoseSign1Codec.cs`, `CwtClaimsCodec.cs`). In that mode `ReadTextString()` decodes a CBOR text string that is not valid UTF-8 lossily, with U+FFFD substitution, instead of rejecting it. RFC 8949 §3.1 requires a text string (major type 3) to be UTF-8, and §5.3.1 classes a non-UTF-8 text string as an invalid data item. This is the CBOR counterpart of the JOSE gap fixed in #28 / #29, found by the #29 adversarial review.

#### Reproduction (on the #29 head)

A protected header whose content type (label 3) is the text string `62 FF FE`:

```
VcCose.Verify  Verified=False  InvalidContentType: VC-JOSE-COSE requires the content type (3) protected header "application/vc"; found "��".
```

`VcCose.Verify` still fails closed here, because it compares against a fixed string. But a text string that is never compared to a constant is accepted with replacement characters: CWT `iss`/`sub`/`aud`, or a text-labelled header. That is the behaviour #29 removes from the JWE header. The review did not observe any exception-contract escape; this is acceptance only.

#### Suggested fix

Read protected headers and CWT claims with `CborConformanceMode.Strict`, which validates UTF-8. If Lax is needed elsewhere, read text strings via `ReadDefiniteLengthTextStringBytes` and check them with `Utf8.IsValid`. Then surface the failure through the existing structured `CoseVerificationFailure` result.

#### Acceptance

- Tests with a non-UTF-8 text string as a protected-header value, a text header label and each CWT text claim, asserting a structured failure.
- Each test shown to fail with the fix reverted.
