# Issue #44: bbs-2023 base proofs through a key store (no raw private key)

Owner's intent (2026-11-20): "Address issue #44". The issue asks for a way to create a `bbs-2023` base proof with a
BLS12-381 G2 key that stays inside a key store. It is done when a base proof created that way verifies and derives
exactly like one from the raw-key method, with identical output for fixed inputs, and when no API on that path
accepts private-key bytes. Downstream: moisesja/credentials-dotnet#43, whose PRD forbids raw private keys.

## Decisions

Owner, 2026-11-20 (asked before planning):
1. **API shape: a key-store reference.** It takes NetCrypto `ICapableKeyStore` + `alias` + `KeyInstanceId`, with no
   new types. The alternative was an `IBbsSigner` seam plus a shipped adapter: three public items and a parallel
   signer surface, which NetCrypto's `ICapableKeyStore` docs say it exists to avoid.
2. **Release: folded into 2.1.0**, which is prepared on main but not tagged. The addition is additive, so it stays a
   minor. No tag, no release.

Made in the plan (the owner approved it):
3. The public key comes from the store, through the instance-checked `GetInfoAsync(alias, instanceId)`.
   - No such key instance: `KeyNotFoundException`, as `SignBbsAsync` documents for the same condition.
   - Another key type, or a public key that is not 96 bytes: `ProofGenerationException`.
4. The HMAC key stays caller-supplied, 32 bytes. It is not signing-key material: the holder receives it inside the
   base proof.
5. The instance id is required. The algorithm is fixed to `KeyStoreAlgorithms.BbsBls12381Sha256`.
6. The store's signature must be 80 bytes and verify under the public key over the messages and header before the
   proof is packed. This costs one BBS verify per issuance.
7. `BbsUnavailableException` is raised before the store is called.
8. Store exceptions propagate unchanged (FR-2 precedent).
9. Input validation runs before the first store call. A pointer that matches nothing is found only during
   transformation, after `GetInfoAsync`, and still before signing.

Made during implementation:
10. **A separate name, `CreateBaseProofWithKeyStoreAsync`, not an overload.** Two `CreateBaseProofAsync` overloads that
    both have an optional `CancellationToken` fail the build with RS0026. Repo precedent is a named entry point:
    `VerifyWithCertificateChainAsync` (#46) and `IssueWithTypeMetadataAsync` (#47, whose plan records the same
    RS0026 reasoning). The parameters are those the owner chose.
11. **Copies at the trust boundary.**
    - The HMAC key and the mandatory pointers are copied at entry: the method awaits the store, and they are packed
      after it.
    - The store gets copies of the messages and header, so its signature is checked against what the suite
      computed.
    - The returned signature is copied before it is checked, so the bytes checked are the bytes packed.
12. The `NotSupportedException` message of `CreateProofAsync(ISigner)` now names both methods.
13. The sample's HMAC key comes from `RandomNumberGenerator.GetBytes(32)` instead of `new Random(42)`. NetCrypto has
    no public randomness API (BannedSymbols.txt).
