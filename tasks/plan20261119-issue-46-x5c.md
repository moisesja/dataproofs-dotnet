# Plan — issue #46: `x5c` in the protected header, end-entity key on verification

Branch `feat/issue-46-x5c`, from `origin/main` (c4bf7fb) fast-forwarded to #47's head (8c898ae, PR #55, which
carries #54 and #52). Release fixed by the owner as **2.1.0, a minor**: additive API only, nothing public changes.
PR review is the gate for this run, so there is no separate plan check-in.

## Owner's intent

Issue #46: "Support the `x5c` header parameter (RFC 7515 §4.1.6) on compact JWS, so SD-JWT VC issuers can be
identified by an X.509 certificate." Downstream: moisesja/credentials-dotnet#33, which owns the trust-anchor
policy ("the library validates chains against caller-supplied anchors only"; "no built-in trust list ships").

Done when (quoted from the issue):
- Signing with a chain and verifying with the key taken from the header round-trips.
- A JWS whose signature does not match the end-entity key fails.
- A malformed `x5c` (not an array of base64 DER certificates) is a parse failure with a stable code.

Plus the parent's constraints: a certificate taken from `x5c` is never its own trust anchor; the signature is
checked with the end-entity key; `ac-6` (crypto through NetCrypto only), `ac-7`, `ac-9`, `ac-12`; PRD, CHANGELOG.

## What the sources say (read 2026-11-19)

- RFC 7515 §4.1.6: "Each string in the array is a base64-encoded (Section 4 of [RFC4648] -- not
  base64url-encoded) DER [ITU.X690.2008] PKIX certificate value. The certificate containing the public key
  corresponding to the key used to digitally sign the JWS MUST be the first certificate. … The recipient MUST
  validate the certificate chain according to RFC 5280 [RFC5280] and consider the certificate or certificate
  chain to be invalid if any validation failure occurs."
- draft-ietf-oauth-sd-jwt-vc-27 §2.5, Inline X.509 Certificates: "When the protected header of the Issuer-signed
  JWT contains the x5c parameter …, the recipient uses the public key from the end-entity certificate … and
  validates the X.509 certificate chain according to Section 4.1.6 of [RFC7515] and [RFC5280] against a trust
  anchor permitted for the Issuer according to policy (a certificate in the x5c header parameter is not a trust
  anchor merely because it is included there). In this case, the Issuer of the Verifiable Digital Credential is
  the subject of the end-entity certificate. An iss claim, if present, is not authenticated by this mechanism".
  Same section: "The recipient's policy determines which mechanism applies to an Issuer; the SD-JWT VC does
  not." §7.3: "A Verifier MUST ensure that for any given Issuer, an attacker cannot influence the type of
  verification process used." Appendix C, -24: "Require x5c to be in the protected header".
- NetCrypto 1.7.1 (`NetCrypto.xml`): no X.509 type, no certificate parser, no path validation, and no RSA
  `KeyType` (Ed25519, X25519, P-256, P-384, P-521, secp256k1, BLS12-381). `JwkConverter.ToPublicJwk` decodes
  SEC1 points and rejects off-curve points (spike: `CryptographicException`) and the identity (`ArgumentException`).
- `BannedSymbols.txt` does not list `System.Security.Cryptography.X509Certificates` or `System.Formats.Asn1`.
  PRD §2.2 still forbids cryptography outside NetCrypto in `src/`, and `ac-7`'s allowlist forbids
  `System.Security.Cryptography.*` in public signatures.

## Decisions

1. **Version: 2.1.0 minor.** Every addition is a new member or an `init` property. No signature changes, no
   optional parameter added to an existing member, no change to any existing path's accepted input or output.

2. **The library parses `x5c` and hands the chain to a mandatory caller hook; it does not validate the chain
   (RFC 5280).** Alternatives:
   - *Validate in the package with `X509Chain` (CustomRootTrust).* Lost: the platform chain engine verifies
     certificate signatures with OS crypto, bypassing NetCrypto (PRD §2.2 / `ac-6`), behaves differently per OS,
     and `ac-7` bars its types from the public API, so trust anchors could not even be passed in as
     `X509Certificate2`. It belongs in the caller, where the sample and tests use it.
   - *Implement RFC 5280 §6 path validation in the package over NetCrypto.* Lost: NetCrypto has no RSA, which most
     CA hierarchies use, so it could not validate most real chains; and the algorithm (name chaining, validity,
     basic constraints, key usage, critical extensions, name constraints, policies, revocation) is a project of
     its own, far beyond this issue. That is a NetCrypto work item if ever wanted.
   - *Parse only, and leave the caller to compose `parse → validate → verify(_ => leafKey)`.* Lost: nothing then
     stops a caller from verifying with the leaf key and skipping validation, which is exactly "a certificate in
     x5c treated as its own trust anchor"; and nothing forces the key used to be the end-entity's.
   With the hook, the library chooses the key (always `x5c[0]`), checks the signature with it, and returns a
   verified result only when the caller's hook returned `true` for that exact chain. The docs and CHANGELOG say
   plainly what the hook must check and what the library does not. This matches credentials-dotnet#33, which owns
   the anchors.

3. **DER parsing uses `System.Formats.Asn1` (`AsnReader`, DER rules).** In-box in the .NET 10 shared framework,
   so no package reference and no change to any nuspec; not cryptography; AOT-safe. Spike: DER rules reject
   non-minimal and indefinite lengths and truncation, and nesting does not recurse (a 480 KB nest reads in 0 ms).
   Alternative `X509CertificateLoader`: lost, it is platform crypto, accepts PEM, and differs per OS.

4. **Mechanism selection is the caller's, by method.** New methods take the hook *instead of* the `kid`
   resolver; the existing `kid` methods ignore `x5c` exactly as today. Alternatives: an `x5c` validator on
   `SdJwtVerificationOptions` beside the required `kid` resolver (lost: either the resolver is ignored, which is a
   confusing required parameter, or the token's content picks the mechanism, which §7.3 forbids); overloads of the
   existing names taking a different delegate or class (lost: `Verify(p, null!)` and `_ => throw …` lambdas become
   ambiguous, a source break).

5. **Signing: an `init` property `JwsSigner.CertificateChain`.** It flows into every compact and JSON JWS, JWT,
   SD-JWT and SD-JWT VC the signer produces, always in the protected header. The setter rejects a chain whose
   end-entity key is not the signer's key (`ArgumentException`), so the library never emits an `x5c` that cannot
   verify. Alternatives: a new `BuildCompactAsync` overload plus an `SdJwtIssuerOptions` property (lost: two
   additions for one fact, and the key check would be split from the key); an optional constructor parameter
   (lost: replaces the constructor's method token, a binary break the brief says to avoid).

6. **Verification surface.** `JwsParser.ParseCompactWithCertificateChain`, `SdJwtVerifier.VerifyWithCertificateChain`,
   `SdJwtVcVerifier.VerifyWithCertificateChainAsync` (Type Metadata processing optional through #47's
   `TypeMetadataProcessingOptions`, so one method covers both of #47's modes; the retrieval-only resolver is not
   offered on the new path because -27 §5.7 requires processing before use). Results gain `CertificateChain` /
   `IssuerCertificateChain`. Not done: detached-payload compact and JSON-serialization verification with `x5c`
   (the issue scopes compact; `JwsParser.Parse` never reads `x5c`, protected or not).

7. **Order on verification:** parse `x5c` → signature with the end-entity key → hook → (SD-JWT) disclosures, Key
   Binding, profile rules. The hook never sees a chain whose key did not verify the signature. A hook exception
   propagates, as a throwing `kid` resolver does today.

8. **`kid` under the `x5c` mechanism** is not reported: `SignerKid` is empty and `SignerKidIsProtected` is
   `false`. The `kid` did not select the key and nothing binds it to the certificate (-27 §2.5: inputs of another
   mechanism do not identify the Issuer). Rejecting `kid` + `x5c` was rejected: both are legal together.

9. **Stable codes.** `X5C_MISSING`, `X5C_MALFORMED`, `X5C_UNSUPPORTED_KEY`, `X5C_UNTRUSTED` start the message (the
   SD-JWT verifiers' `Errors`, the exceptions' `Message`), like the existing `ISSUER_*` and `VC_*` codes. A
   signature that does not verify under the end-entity key keeps the existing outcome (`JoseCryptoException`,
   `ISSUER_SIGNATURE_INVALID`). `JwsParser` throws `MalformedJoseException` for `X5C_MALFORMED` and
   `JoseCryptoException` for the others, matching its existing split.

10. **What a well-formed `x5c` is.** A JSON array of 1 to `X509CertificateChain.MaxCertificates` (10) strings;
    each canonical RFC 4648 §4 base64 (padding required; no whitespace, no base64url alphabet, no non-zero pad
    bits); each a DER `Certificate` with nothing after it, whose `TBSCertificate` fields are in RFC 5280 order;
    no two identical. The end-entity key must be Ed25519, P-256, P-384 or secp256k1 (the v1 JWS curves, FR-13);
    anything else is `X5C_UNSUPPORTED_KEY`. Order and uniqueness beyond byte equality are path validation, the
    hook's job. DEFAULT values encoded explicitly (an explicit v1 version, an explicit critical FALSE) are
    tolerated, as certificate parsers generally do. (The first draft read Names, parameters and extension values by
    their outer TLV only; decision 14 corrects that.)

11. **Ed25519 end-entity keys are length-checked only (moved during the adversarial pass, finding F1).** The first
    draft's docs promised `X5C_MALFORMED` for any invalid key encoding, but 32 bytes that do not decode to an
    Ed25519 point were accepted. Alternatives: decode the point here (RFC 8032 §5.1.3: y < p, a square root, the sign
    rule) and reject small-order points — lost, it is curve arithmetic outside NetCrypto (PRD §2.2: "If a primitive
    is missing, it is a NetCrypto work item, not a local shim"), and NetCrypto's `EcPointValidator` covers EC curves
    only; a NetCrypto change is a sibling-repository change. Kept: the same posture as an Ed25519 JWK
    (`JwkConversion` checks 32 bytes), with the point decoded by the signature check (RFC 8032 §5.1.7 step 1), which
    fails closed before the hook runs. The docs now say so and a test pins it. The adversary tried small-order
    forgeries (7 keys × 128 attempts, both paths) and none verified.

13. **The library refuses an end-entity whose Key Usage lacks `digitalSignature` (review round 1, P2).** The reviewer
    showed a trusted, CA-signed, critical keyAgreement-only leaf verifying on all three APIs: `X509Chain`, and so the
    sample hook, does not check what the end-entity key is for. Alternatives: enforce it only in the sample hook and
    the test helper, as the reviewer asked (lost: it protects only hooks that copy the sample, and every hook needs it,
    because it limits the use the library itself makes of the key, which is to verify a signature); leave it to the
    hook and document it (lost, same reason). Kept: RFC 5280 §4.2.1.3, "When present, ... the key usage extension
    defines the purpose ... of the key contained in the certificate", so when the extension is present the end-entity
    must assert `digitalSignature` (bit 0), critical or not, before the key is used and before the hook:
    `X5C_KEY_USAGE` on the verifiers, `ArgumentException` on the signer. No extension means unrestricted.
    `contentCommitment` alone is refused: it names the non-repudiation service, and issuer signatures authenticate.
    `Create` still accepts such a chain, since it is well formed. The hook and the sample do not repeat the check;
    the sample now shows the refusal. Only the end-entity: a CA's `keyCertSign` is path validation.
14. **Extended Key Usage stays with the hook.** RFC 5280 §4.2.1.12 restricts a certificate with the extension to its
    listed purposes, but there is no generic purpose for "JWS / SD-JWT VC issuer": ecosystems define their own (ISO
    18013-5's document-signer EKU, for one). A library rule would either refuse those issuers or accept any EKU,
    which checks nothing. The docs say so and the sample's hook comment points at `X509EnhancedKeyUsageExtension`.
15. **Every certificate TLV is read under DER rules (review round 1, P3).** The reviewer's `30 02 31 01` Name (a
    SEQUENCE holding a truncated SET) was accepted, because Names, parameters and extension values were skipped by
    their outer TLV. Alternatives: narrow the contract to "the outer structure" (lost: #46 asks that a value that is
    not "base64 DER certificates" be a parse failure, and a truncated TLV inside a Name is not DER); full ASN.1 schema
    validation of every extension type (lost: dozens of extension schemas, and unknown extensions are legal). Kept:
    Names to their attribute values (non-empty RDN SETs in DER order, `{OID, value}`), each `extnValue` exactly one
    DER TLV, no repeated extension (RFC 5280 §4.2), and a bounded walk (depth 32) of every value the schema leaves open
    with DER's content rules for the primitive types it constrains; string bytes, OCTET STRING bytes and the
    signature and non-end-entity key BIT STRINGs are not interpreted, and the docs say exactly that. False-reject
    check before committing: the RFC 7515 Appendix B chain (vendored) and all 128 roots in the macOS bundle parse
    (23 end-entity-capable, 105 RSA, `X5C_UNSUPPORTED_KEY` as end-entity keys); none is `X5C_MALFORMED`.

16. **Schema-unknown values are checked only against DER rules that hold whatever the schema (review round 2, P3).**
    Round 1 read every universal SET in an open value as a SET OF, so the reviewer's valid tag-ordered SET was refused.
    The rules the open-value reader applies, each against X.690 (2021), with whether it holds for every DER value
    regardless of schema:

    | Rule | Holds without the schema? | Kept |
    | --- | --- | --- |
    | Definite length in the fewest octets (§10.1, §8.1.3) | Yes: DER requires it of every encoding | Yes |
    | Minimal tag octets (§8.1.2.4) | Yes: a BER rule for every tag | Yes |
    | A constructed encoding's contents are complete TLVs (§8.1.3.1) | Yes: by definition | Yes |
    | Primitive form for BOOLEAN, INTEGER, BIT STRING, OCTET STRING, NULL, OID, ObjectDescriptor, REAL, ENUMERATED, RELATIVE-OID, the restricted strings, UTCTime, GeneralizedTime (§8.2–§8.20, §10.2) | Yes: a universal tag fixes the type; implicit tagging changes the tag | Yes |
    | Constructed form for SEQUENCE, SET, EXTERNAL, EMBEDDED PDV, CHARACTER STRING (§8.9–§8.12, §8.18, §8.24) | Yes | Yes (round 1 refused constructed EXTERNAL and the other two, and accepted their primitive forms) |
    | No END-OF-CONTENTS (§10.1: no indefinite length) | Yes | Yes |
    | BOOLEAN one octet, 00 or FF (§8.2.1, §11.1) | Yes | Yes |
    | INTEGER, ENUMERATED minimal (§8.3.2, §8.4) | Yes | Yes |
    | BIT STRING unused bits 0–7, zero, 0 when empty (§8.6.2, §11.2.1) | Yes | Yes |
    | BIT STRING named-bit trailing zeros removed (§11.2.2) | No: only for a named bit list | Not checked |
    | NULL empty (§8.8.2) | Yes | Yes |
    | OID subidentifiers minimal (§8.19.2) | Yes | Yes |
    | UTCTime and GeneralizedTime in DER form (§11.7, §11.8) | Yes | Yes |
    | SET components in tag order (§10.3) | No: only for a SET, and an untagged CHOICE sorts by its least tag (X.680 §8.6), not its encoded one | Dropped (round 1 applied the SET OF rule instead) |
    | SET OF components in octet order (§11.6) | No: only for a SET OF | Dropped for open values; kept for the RDN, whose schema is known |
    | DEFAULT values omitted (§11.5) | No: needs the schema | Not checked |
    | String character sets, UniversalString/BMPString length multiples | No: type constraints, not encoding rules | Not checked |
    | Nesting at most 32 | Not a DER rule: a resource bound | Kept, documented as a bound |

    False-reject check after the change: the vendored RFC 7515 Appendix B chain; platform-validated certificates with
    certificatePolicies (EV with CPS and UserNotice, ETSI QCP), eIDAS qcStatements (QcCompliance, QcType, QcPDS,
    semantics, QcEuLimitValue, retention), a CT SCT list, AIA, CRL distribution points, every SAN form .NET builds,
    EKU, SKI, AKI with issuer and serial, and Names in every common string type with a multi-valued RDN (committed
    tests); and, locally, 349 distinct real certificates from `/etc/ssl/cert.pem`, the macOS system roots and
    System.keychain, and the signing chains of 725 cached NuGet packages: none `X5C_MALFORMED` (68 parse, 281 RSA are
    `X5C_UNSUPPORTED_KEY` as end-entities). The extensions in that set include certificatePolicies, AIA, CRL DP, EKU,
    SAN, name constraints, logotype, Netscape and Microsoft and Apple private extensions, and a SET extension.
17. **Test certificates are deterministic (review round 2, P2).** The malformed-`x5c` fixture took the first of eight
    randomly signed certificates whose length was not a multiple of 3; each is one with probability about 1/2 (measured
    on 50a2d09: 199 of 400), so generation failed about 1 time in 256. Alternatives: more candidates (lost: still
    probabilistic, as the reviewer said). Kept: assembled certificates are signed by a seeded Ed25519 key
    (deterministic, 64-byte signatures) with a fixed validity and an 8-byte serial, so their length depends only on
    their inputs; the padded fixture picks one of three subject lengths deterministically. Audit of the other new
    tests: platform-made chains (`CreatePki`) still use random ECDSA keys and signatures, but no test reads their
    length; the off-curve key row now uses a seeded key; the remaining random keys only feed signatures that must not
    verify, which they would only by breaking the scheme.

12. **The hook is synchronous** (`Func<X509CertificateChain, bool>`), like the `kid` resolver it replaces. A verifier
    doing online revocation blocks inside it, as `X509Chain.Build` does anyway. An async hook is listed as not done.
