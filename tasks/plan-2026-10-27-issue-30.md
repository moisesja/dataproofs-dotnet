## Context
Issue #30 is **valid**. I reproduced every claim at HEAD (`a714e61`) with a scratch console wired to the real `DataProofsDotnet.Jose` project.

- **Lone-surrogate escapes** (`\uD800`, `\uDC00`, `\uD800A`) throw a raw `InvalidOperationException` from all of these:
  - `SdJwtVerifier.Verify`: the issuer header (member name, `alg`, `kid`), the payload `_sd_alg`, and an appended Disclosure.
  - `SdJwtVcVerifier.VerifyAsync`: `typ`.
  - `JwsParser.Parse`: `payload`, `protected`, an unprotected member name, an extra top-level member.
  - `JweParser.Parse`, `PeekRecipients` and `ParseAsync`.
  - `VcJose.VerifyCredential`: `cty`.
  - `JwtClaims.Parse`, and `JwtHandler.Verify` on `iss`.
- **Model poisoning:** a signed `{"iss":"i","x":"\uD800"}` → `JwtHandler.Verify` reports `IsValid=True`. The consumer's later `GetValue<string>()` or `ToJsonBytes()` then throws.
- **Non-object claims root:** `JwtClaims.Parse` with `[]`, `42`, `"x"` or `true`, and `JwtHandler.Verify` with a signed `[]` payload, throw `InvalidOperationException`.
- **Empty JWE `protected`:** `JweParser.Parse`, `PeekRecipients` and `ParseAsync` throw `ArgumentException`. The JWS counterpart already returns `MalformedJoseException`.
- **Found beyond the report:** a lone surrogate in a **compact JWS or JWE header extension value** is accepted at decode time. The same value in a member name or a modelled field is rejected. Paths that should behave alike today don't.

**Spike (scratch project, .NET 10.0.100):**
- `Utf8JsonReader.GetString()` throws `InvalidOperationException` for all three escapes and for `\uD800\uD800`, on both `String` and `PropertyName` tokens. A valid surrogate-pair escape (U+D83D U+DE00 as two six-character escapes) reads fine.
- `ValueIsEscaped` is `false` for unescaped tokens. `Utf8.IsValid` rejects encoded surrogates (`ED A0 80`). An unescaped token in validated UTF-8 therefore always transcodes, so the scan only needs to transcode escaped tokens.
- A leading BOM is rejected identically by `Utf8JsonReader`, `JsonDocument`, `JsonNode` and `JsonSerializer`. Max depth 64 is identical across all four. The reader and the parsers accept the same grammar, so there is no parser differential.
- `JsonMarshal.GetRawUtf8Value(doc.RootElement)` returns the parsed document's UTF-8 bytes with no copy.
- `JsonObject.Create` on a non-object root throws, as the issue says.
- **The library's own typed serializers never emit a lone-surrogate escape.** They substitute U+FFFD (checked for `JwtHandler.SignAsync`, the `JwsSigner` kid, `typ` and `SdJwtIssuer`). Only raw caller bytes passed to `JwsBuilder` can carry one.

**Normative basis for rejecting it:** RFC 8259 §8.2 lets the grammar contain an unpaired surrogate escape, but says the receiver's behaviour is "unpredictable". RFC 7493 (I-JSON) §2.1 says member names and string values "MUST NOT include code points that identify Surrogates". System.Text.Json cannot read such a string at all. So these escapes are **grammatically valid JSON, but not Unicode text**. Under RELEASING.md this is a **spec-valid accept-set narrowing, which is minor material**. 1.4.0 is already a minor, so this is consistent, and the CHANGELOG will say so plainly.

## Approach: one control at the decode boundary, plus two targeted fixes

### 1. `Json/JoseJson.cs`: replace `RequireUtf8` with `RequireTranscodableJson(ReadOnlySpan<byte> utf8Json, string what)`
- Runs `Utf8.IsValid` first, with the unchanged `"{what} is not valid UTF-8."` message, so every #28 test keeps passing.
- Then makes one `Utf8JsonReader` pass with default options. For each `String`/`PropertyName` token where `ValueIsEscaped` is true, it calls `GetString()`. An `InvalidOperationException` there becomes `MalformedJoseException("{what} contains an unpaired UTF-16 surrogate escape.")`.
- A reader `JsonException` throws `MalformedJoseException("{what} is not valid JSON.")` rather than being swallowed. This fails closed: if a parser's options ever drift looser than the reader's, the scan still rejects instead of being bypassed.
- O(n). Allocates only for escaped tokens. AOT-safe.
- The remarks are rewritten, and the "known 1.4.0 limitation, tracked in issue #30" text is removed.

### 2. Call it at every JSON decode site in Jose
That is all five base64url-decoded sites and both outer-JSON sites.
- **Decoded sites:** each `RequireUtf8` call is replaced in place.
  - `JwsProtectedHeader.DecodeCore`
  - `JweProtectedHeader.Decode`
  - `JwtClaims.Parse`
  - `CompactJwt.DecodeJsonObject`, which covers the issuer JWT and the KB-JWT
  - `Disclosure.Parse`

  This one change closes every pre- and post-signature site in the issue: KB-JWT `typ`/`aud`/`sd_hash`/`nonce`, `_sd` digests, `...` placeholders, `cnf.jwk`, `JwtHandler` claims and model poisoning.
- **Outer JSON text:** in `JwsParser.ParseJsonCore` and `JweParser.ParseStructure`, the first statement inside `using (doc)` becomes `JoseJson.RequireTranscodableJson(JsonMarshal.GetRawUtf8Value(doc.RootElement), "JWS"/"JWE")`. The existing `JsonDocument.Parse(string)` and its `ArgumentException` (UTF-16) handling stay as they are.
- Swept: every `GetValue<string>()` in SdJwt and Jwt is already guarded by a `GetValueKind()` check, so once strings are known to transcode, no other `InvalidOperationException` source remains on these paths.

### 3. `JwtClaims.Parse`: non-object root
Check `doc.RootElement.ValueKind != JsonValueKind.Object` before `JsonObject.Create` and throw the existing `"JWT claims set is not a JSON object."`. This also covers `null`, so the redundant `node is not JsonObject` guard collapses.

### 4. `JweProtectedHeader.Decode`: empty input
Replace `ArgumentException.ThrowIfNullOrEmpty(encoded)` with `MalformedJoseException("JWE protected header is empty.")`, mirroring `JwsProtectedHeader.DecodeBytes`.

### 5. Defence in depth (the issue's "move reads inside the existing try")
`CompactJwt.Decode` resolves `typ` and `kid` eagerly, next to `alg`, which it already resolves. `Type` and `KeyId` become plain field reads. Then no header read can happen outside the callers' `try`. That covers `SdJwtVerifier`'s `KeyId` and `SdJwtVcVerifier`'s `Type`, and the semantics don't change. The existing `catch (InvalidOperationException)` in `JwsProtectedHeader.DecodeCore` stays, with its comment updated from "load-bearing" to defence in depth. **I'm deliberately not adding a blanket `catch (InvalidOperationException)` at the entry points.** The decode boundary is the control, and a catch-all would hide real bugs.

## Tests: new `tests/DataProofsDotnet.Jose.Tests/Hardening/Issue30ContractEscapeTests.cs`
These follow the `Issue28InvalidUtf8Tests` and `InvalidUtf8SweepTests` style, with one case per theory row. The escapes tested are `\uD800`, `\uDC00`, `\uD800A` and `\uD800\uD800`.
- **JWS protected header, genuinely signed:** flattened, general, compact, vcjose, flattened-detached and compact-detached, each × {member name, `kid` value, extension value, `cty` value} × escape. The assertion is `MalformedJoseException` matching `*unpaired*surrogate*`, with the resolver never called.
- **JWS outer JSON:** `payload`, `protected`, `signature`, unprotected `kid`, unprotected member name, extra top-level member name, `signatures[]` entry member name. Run through `Parse` (flattened and general) and detached.
- **JWE outer JSON and decoded header:** `protected`/`iv`/`ciphertext`/`tag`/`encrypted_key`/recipient `kid`/member names, plus header {member name, modelled field, extension value}. Run through `Parse`, `PeekRecipients` and `ParseAsync`, and the compact entry points for the header.
- **JWT:** `JwtClaims.Parse` and `JwtHandler.Verify` (signed through `JwsBuilder` with raw bytes) over claim name, `iss`/`sub`/`jti`, `aud` string and array element, unregistered value, nested key and value. Includes the model-poisoning case, which must now give `IsValid=false` with a single `MALFORMED` error and never throw.
- **SD-JWT and SD-JWT VC:**
  - Unauthenticated: the issuer header (member name/`alg`/`kid`/`typ`/extension) and payload (member name/`_sd_alg`/value), plus appended Disclosures (salt/name/value/nested/array element). These must give a structured `MALFORMED`.
  - Malicious issuer, hand-signed: `_sd` digest, `...` placeholder, `cnf.jwk` member.
  - **KB-JWT end to end:** a genuine issuance with `cnf`, and a KB-JWT genuinely signed by the holder with the escape in `typ`, `aud`, `sd_hash`, `nonce` or a member name. This must give `KB_JWT_MALFORMED`. A genuine signature is what proves the path used to crash after the signature check.
  - `Disclosure.Parse` and `SdJwtComponents.Parse` directly.
- **Non-object root:** `JwtClaims.Parse` with `[]`, `42`, `"x"`, `true` and `null`, and `JwtHandler.Verify` with each signed root.
- **Empty JWE `protected`:** `Parse`, `PeekRecipients` and `ParseAsync` → `"JWE protected header is empty."`.
- **Over-rejection guards:** a surrogate-pair escape, a BMP escape (U+00E9) and `\/` still verify on every JWS entry point, the JWE outer JSON and header, `JwtHandler.Verify` (decoded values asserted) and an SD-JWT with an escaped Disclosure value.
- **Revert proof:** stash `src/` only, run `--filter Issue30`, and record that every negative case fails while the guards pass. Then restore.

## Decisions during implementation

- **The outer-JSON check moved before the parse (deviation from the approved plan).** The plan put
  the JWS/JWE JSON-serialization check *after* `JsonDocument.Parse(string)`, over
  `JsonMarshal.GetRawUtf8Value`. The first test run showed 64 failures, all member-name placements:
  `JsonDocument.Parse` with `AllowDuplicateProperties = false` transcodes every member name in its
  own duplicate check (`ValidateDuplicatePropertiesCore` → `GetUnescaped`) and throws
  `InvalidOperationException` itself — a channel the issue did not list and the spike did not
  probe (it parsed without the strict option). Fix: `JoseJson.ParseStrictDocument(string, what)`
  transcodes the caller's string with a throwing `UTF8Encoding`, runs `RequireTranscodableJson`,
  then parses the bytes. It replaces the duplicated parse blocks in `JwsParser.ParseJsonCore` and
  `JweParser.ParseStructure` and keeps their exact messages ("… is not valid JSON.", "… is not valid
  JSON text: the string is not well-formed UTF-16."). The decoded sites were unaffected: their check
  already ran before their parse. The same duplicate-check channel is worth noting on #33, whose
  Core pipeline parses with duplicate rejection too.
- **Messages are asserted exactly** in the new tests, so each negative case fails against the
  pre-fix code whichever way that code mishandled the input (raw exception, a different
  `MalformedJoseException` message, a later `JoseCryptoException`, or acceptance).
- Verified before writing the CHANGELOG's accept-set claim: `JweBuilder` (protected `typ`, recipient
  `kid`, compact `kid`) and `KeyBindingJwt.IssueAsync` (`nonce`, `aud`) write a lone .NET surrogate
  as U+FFFD, like `JwtHandler.SignAsync`, `JwsBuilder`'s headers and `SdJwtIssuer`.

## Review

**Outcome.** Issue #30 is valid and closed in full, with three more pre-existing JWE contract
escapes from the adversarial review (low-order X25519 key, malformed ECDH-1PU sender key, signing
curve on `ParseCompact`). A single control, `JoseJson.RequireTranscodableJson`, sits at every JOSE
JSON decode boundary. For the JWS/JWE JSON serializations it runs through
`JoseJson.ParseStrictDocument`, before the parse. No public API changed and no emitted bytes changed;
the `IEcdhKey` XML docs gained an `<exception>` contract.

**Evidence.**
- 788 regression cases (`Hardening/Issue30ContractEscapeTests.cs`). Against `a714e61`'s src
  (before the pass-2 fix, 786 cases): 756 fail and 30 pass. The 30 are exactly the over-rejection
  guards, the own-output round trips, the controls and the `null`-root pins. The P2-1 cases fail
  separately against the pre-fix parser.
- Mutation: an all-surrogates over-rejection mutant fails 23 guards.
- Full gate: solution Release build `/warnaserror` clean; **1812 tests, 0 failed, 0 skipped**.
  AOT smoke JIT, reflection-disabled and native-AOT (osx-arm64) legs: 44/44 each, `compare`
  identical, `verify` 32/32. The publish log's IL warnings are the canary and the known
  Newtonsoft.Json set only.

**What went wrong and was caught.**
1. The plan put the envelope check after `JsonDocument.Parse`. The duplicate-member validation
   throws first, so 64 rows failed on the first run; fixed before the first commit.
2. The guard escapes were decoded by the Write tool. The reviewer caught it; fixed, and
   mutation-verified.

Both are recorded in `tasks/lessons.md`.
