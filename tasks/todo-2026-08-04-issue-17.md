# Issue #17 — JwsBuilder duplicates `kid` in protected and unprotected headers (RFC 7515 §7.2)

Release target: **v1.2.0** (user request).

## Problem

`JwsBuilder.SignOneAsync` stamps the signer `kid` into the integrity-protected header, then
`RenderFlattened`/`RenderGeneral` render the same `kid` again in the per-signature unprotected
`header` object. RFC 7515 §7.2 requires the protected/unprotected header parameter-name sets to
be disjoint; strict verifiers (nimbus-jose-jwt, used by didcomm-jvm) reject every such JWS.

## Fix (per the issue's proposed fix — protected-only kid)

- [x] `JwsBuilder.RenderFlattened` / `RenderGeneral`: never emit the unprotected `header`
      object. The `kid` is always already in the protected header (signed), which is where
      `JwsParser` prefers it since #10 and where the RFC 7520 cookbook shapes put it.
      `SignatureEntry.Kid` becomes dead — remove it.
- [x] Regression tests (issue's ask): assert protected/unprotected header parameter-set
      disjointness for both serializations — Flattened (1 signer) and General (2 signers):
      no `header` member at all in the output; `kid` present in the protected header; a full
      build → parse → verify round-trip still surfaces `SignerKid`.
      Lesson check (2026-07-27): fixtures here are *builder outputs*, asserted against the
      spec-conformant shape — no nonconformant fixture asserted as valid.
- [x] CHANGELOG: new `## [1.2.0]` entry (Fixed).
- [x] `Directory.Build.props`: `DataProofsVersion` 1.1.1 → 1.2.0 (dev default).
- [x] Full solution build (warnings-as-errors) + test run.
- [x] Adversarial review subagent on the change before declaring done.

## Review

- Fix shipped exactly as the issue proposed: neither JSON serialization emits the unprotected
  `header` object any more; the `kid` lives only in the signed protected header.
  `SignatureEntry.Kid` and both kid-branches in the renderers deleted. Kid-less output is
  byte-identical to before (RFC 7520 cookbook byte-match still green); compact untouched.
- Frozen ES256K vector re-pinned (only the `header` member removed — signature bytes identical
  per RFC 6979); `xc20p.json` left alone so its random ECDH-ES ephemeral doesn't churn.
  PROVENANCE.md records the re-pin.
- Regression tests (`Rfc7515HeaderDisjointnessTests`): Flattened, General, and both detached
  variants — assert protected/unprotected parameter-name-set disjointness, kid present in every
  protected header, and parse+verify round-trips surfacing the right `SignerKid`.
- Adversarial review subagent: all seven attack angles CONFIRMED-SAFE; its one finding (the
  detached render branches were untested) was closed with the detached test above. Residual
  note: external verifiers that read ONLY the unprotected kid (DIDComm convention) must fall
  back to the protected header — disclosed in the CHANGELOG for 1.2.0 consumers.
- Full suite green: 836 tests / 7 assemblies, Release, warnings-as-errors.
